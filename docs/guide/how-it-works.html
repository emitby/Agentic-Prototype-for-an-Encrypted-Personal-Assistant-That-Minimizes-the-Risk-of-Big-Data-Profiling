1. Why this app protects your personal data

Most assistants keep your data on someone else's servers and send everything you type to a model. Over time that builds a detailed profile: your accounts, habits, travel and purchases. This assistant is designed around one question: how much can an AI assistant do for you while sending as little as possible about you to anyone else?

Principles

  • Encrypted at rest, on your machine. Everything (accounts, emails, lists, supplies, travel preferences, even the chat transcript) is one AES-256-GCM encrypted file inside the project. The key exists only in memory while unlocked.
  • Secrets never reach the AI. Agents work with labels such as github. Passwords, usernames and stored addresses are replaced before anything is sent, and a final scan refuses to send a request that still contains one.
  • You hold the keys. Adding logins, revealing passwords and confirming rotations are terminal commands. No agent has those tools.

Minimization in practice

  • Breach checks by k-anonymity: only 5 hex characters of a password's hash leave the machine, and padded responses hide even which prefix matched.
  • Fresh context per specialist: the Travel Agent never sees your accounts; the Security Agent never sees your groceries.
  • Numbers come from code: supply estimates and breach counts are computed locally, so nothing needs to be sent for the model to "work them out".
  • No telemetry, no accounts, no cloud storage.

2. How the agents work together

A Coordinator reads your (redacted) request and delegates to three specialists. Each specialist starts every task with a fresh context and only its own tools, so data from one area never sits in another agent's context. When a request spans areas, the Coordinator calls the specialists in the same turn and they run in parallel.

3. The vault and its encryption

All stored data is one JSON document, encrypted as a whole. Nothing the assistant keeps is ever written to disk in plaintext.

File format

FieldContentsWhy it matters
vFormat version (1)In the AAD, so it can't be changed undetected
kdf.salt16 random bytes (base64)Makes each vault's key unique; precomputed tables are useless
kdf.n, r, pscrypt cost: 131,072, 8, 1In the AAD: swapping in weaker parameters breaks decryption
nonce12 random bytes, new on every saveGCM must never reuse a nonce with the same key
ctCiphertext + 16-byte authentication tagAny changed bit fails the tag check on unlock

Why these choices

  • scrypt turns your passphrase into the key. It is deliberately slow and memory-hard (about 128 MiB and 0.3-1 s per attempt), so guessing passphrases, even on GPUs, is expensive. The salt makes every vault's key unique.
  • AES-256-GCM both encrypts and authenticates. Changing a single bit of the file, or swapping in weaker scrypt parameters (they're bound in as associated data), makes unlocking fail.
  • A fresh random nonce on every save, because GCM must never reuse a nonce with the same key.
  • Atomic saves: the new file is written as vault.enc.tmp and renamed over the old one, so a crash can't leave a half-written vault. Nothing is deleted.

What this means for you

  • The passphrase and key are never stored. A lost passphrase can't be recovered, by you or anyone else.
  • Someone who copies vault.enc sees only random-looking bytes and must guess the passphrase, one expensive scrypt run per guess.
  • The vault refuses any path outside the project folder.
  • /quit locks the vault: the key and data are dropped from memory.
  • The scenario vaults in the harness use N = 2^14 for speed; real vaults use 2^17.

4. The privacy pipeline

Five layers stand between your data and the AI service, plus one detector. Layers 1-3 keep secrets out by design; layer 4 only detects (it records a tool that returned a secret, so the bug can be fixed); layers 5-6 are code checks that remove a secret or refuse to send.

you> Is my password password123 safe? My username is adalove and my email is ada@example.com.
privacy filter removed before sending: [email:personal], [password:github], [username:github]
guardrails: input_redact: modified
assistant> Password check:
- bank (bank.example): shorter than 12 characters
- github (github.com): appears in known breaches 251,682 times; shorter than 12 characters; same password as shop
- shop (shop.example): appears in known breaches 251,682 times; shorter than 12 characters; same password as github

Above: the user typed a password, username and email into the chat. The filter replaced all three before anything was sent (recorded as the input_redact event), and the scorer no_secrets_sent confirmed none of the seeded secrets appeared in any request.

6. Hooks

A hook is code that runs automatically at a fixed point, before or after something happens, and can stop it or change it. This project uses hooks in two places: inside the assistant, around every model call and tool call; and for AI coding agents (such as Claude Code) that edit this repository.

6a. In-app hooks: the pipeline around every call

Every hook that blocks or changes something emits a hook event, so the trace (and this guide) show exactly which hook acted and why. Hooks run for all four agents from one shared set per session.

6b. Claude Code hooks: keeping AI coding agents inside this folder

Claude Code supports hooks configured in .claude/settings.json. A PreToolUse hook runs before an AI agent's tool call and can block it. This project registers .claude/hooks/guard.py (no os module) for file edits and shell commands. It receives the pending call as JSON and exits 0 to allow or 2 to block, with the reason shown to the agent.

{"hooks": {"PreToolUse": [{
  "matcher": "Write|Edit|MultiEdit|NotebookEdit|Bash|PowerShell",
  "hooks": [{"type": "command",
             "command": "<project .venv python> $CLAUDE_PROJECT_DIR/.claude/hooks/guard.py"}]
}]}}

Limits: the hook matches patterns; it isn't a sandbox, and a command can hide a path (variables, encodings). It catches honest mistakes and obvious attempts, alongside CLAUDE.md's rules. It applies to Claude Code sessions opened in this folder.

How tokens are attributed to tools

  • Decision: the output tokens of the call that requested the tool (reasoning plus writing the call), split by argument size when several tools are requested together.
  • Result: how much the agent's prompt grew on its next call, minus the previous output, split by result size (for web search, by the size of the search results).
  • Specialist: for the three delegation tools, everything the delegated agent's run used.

Per-agent totals are exact sums of reported usage; per-tool numbers are an attribution. Totals include cache reads.

Limits

  • This is a research prototype. Don't make it your only password manager.
  • Requests you make are visible to the AI service after redaction; web searches reveal what you search for.
  • The injection check catches known phrasings; the agents' instructions are the second line of defense.
  • The Claude Code hook is pattern matching, not a sandbox.
  • Token budgets are checked before each call; specialists running in parallel can overshoot by the calls in flight.
  • Per-tool token numbers are attributions; the numbers in this guide are simulated estimates.
